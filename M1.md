# M1: the capture tap — status and design

**Stage 1 is built and verified (2026-11-22).** ReGPU writes the game's frames to a `.fir` capture file in Frame IR
framing with Xenos-native records. **Committed on ReGPU `vulkan`: d828ed8 (the tap) and d540cb0 (vertex fetches from
the microcode, index address)**, not pushed. Same content as
[`regpu/regpu-fir-tap-stage1.patch`](regpu/regpu-fir-tap-stage1.patch) (against 478adb8); also applied, uncommitted, in
the FM3 checkout on 604dd2b and built into its build\rel. Reader: [`tools/fir_read.py`](tools/fir_read.py); stage-2
geometry: [`tools/fir_geometry.py`](tools/fir_geometry.py); transforms, camera and world export:
[`tools/fir_vs.py`](tools/fir_vs.py), [`tools/fir_frame.py`](tools/fir_frame.py), [`tools/fir_world.py`](tools/fir_world.py).

M0 decided what M1 has to respect: FM3's triple frame is bound by ReGPU's draw thread at ~0.75 µs a draw, so the tap
must cost nothing when off, and later stages must take claimed draws off the draw thread before translation.

## Stages

| Stage | What | Status |
|---|---|---|
| 1 | **Xenos-native capture to file.** Per frame: full register snapshot, then per draw/resolve the register delta, draw initiator, index buffer, shader hashes, and refs to index, vertex and texture data; each distinct shader and data blob once per capture (raw bytes; RGBA8 for decodable 2D textures). Triple/VR replays skipped | **Done** |
| 2 | **Offline converter to canonical Frame IR** (Python first): vertex decode from ReGPU's fetch layouts and Xenos formats, primitive conversion (strips, fans, quads, rect lists to triangles), textures from the RGBA8 decode, view/model recovery from constants (with the FM3 profile's camera hook) | **Geometry, per-draw transforms, camera and world export done** (positions only); other attributes, materials next |
| 3 | **Live stream** instead of a file: the same records into a shared-memory ring, canonical conversion moved into ReGPU where cheap | After M3 |
| 4 | **Claims:** a check at the top of `DrawImpl` (before translation) that drops claimed draws from the original path in all three screens, plus `FIR_DRAW_SUPPRESSED` | M5 |

## Stage 1 in detail

Switches (ReGPU, see `src/gpu/fir_tap.h`):

| Switch | Kind | Meaning |
|---|---|---|
| `REGPU_FIR_CAPTURE=<file>` | start-time | The tap is available, writing to that file |
| `REGPU_FIR_ARM` | live | Off → on starts a capture at the next frame |
| `REGPU_FIR_AT=<frame>` | start-time | Or start at that frame number |
| `REGPU_FIR_FRAMES=<n>` | start-time | Frames per capture (default 3) |

Records (private range of `frame_ir.h`): `XENOS_REGS 0xF101` (pairs of register index and value), `XENOS_DRAW 0xF102`,
`XENOS_RESOLVE 0xF103`, `XENOS_SHADER 0xF104` (microcode, fetch layout, constant masks), `XENOS_DATA 0xF105` (index,
vertex, raw texture, RGBA8 texture). Standard `SESSION_BEGIN`, `FRAME_BEGIN`, `FRAME_END`. Hashes are ReGPU's 64-bit
`FullHash` in `lo` and the byte count in `hi` (Frame IR asks for XXH3-128; stage 2 may switch).

Where it hooks (`src/gpu/renderer.cpp`): the draw path at the same point as the F12 trace (everything about the draw is
known there), the resolve branch of `DrawImpl`, and `RendererOnSwap` (frame end, arming). Off: one bool test per draw.

### Verified

- **First capture**, FM3 frozen grid, triple 7680×1440, 4x MSAA: 3 frames, 8,953 draws (~2,980 a frame, 2,328
  main-view), 26-33 resolves, 61 vertex and 108 pixel shaders, 605 vertex buffers, 485 index buffers, 446 textures;
  525.5 MB (375.6 of it the RGBA8 decodes), written in under 1 s. The game kept running (~140 fps after).
- **Integrity:** every record size and blob reference valid; every hash a draw refers to has its data.
- **Stability across frames** (M2's question, early): 98.6 % and 100 % of the next frames' draws reappear with
  identical shaders, buffers and textures. **Draw order is not stable**: by position only 24 % match, so FM3 orders its
  draws differently every frame even on the frozen grid. Tools must match by content (as CORE.md already does).
- **Texture decode:** terrain, sky panorama and car atlases (VW, PT Cruiser, Citroën C4, Mazda 3) decode correctly.
- **Cost when off:** M0's R2 on the tap build without capturing: 145.8 fps both boots (M0: 146).
- The tap compiles on the vulkan tip (478adb8) with FM3's exact flags.

### Limits of stage 1

- Captures are big (the RGBA8 decodes). A switch to leave them out is an easy add when it matters.
- Draws recorded on draw workers (`REGPU_DRAW_WORKERS`) are flagged; their order in the frame is not guaranteed.
  FM3's default is the serial draw thread.
- Hyper cull and other ReGPU skips drop draws before the hook: capture with them off.
- Index data is the whole index buffer the draw points at; the converter cuts the range.

## Stage 2 so far: geometry

[`tools/fir_geometry.py`](tools/fir_geometry.py) converts a captured frame's draws into triangle meshes, deduplicated by
geometry id. It mirrors ReGPU exactly: index reads and restart cuts as `ReadIndex`/`BuildIndexList`, triangle lists,
strips, fans, quad lists and rect lists to triangles, vertex reads with the endian `Swap` modes, formats as `hlsl.cpp`
`Unpack` (incl. Xenos half floats and the exponent adjust). The position is the shader's first vertex fetch (ReGPU's
`positionFetch` rule), in the shader's object space.

**Result (FM3 triple grid, one frame):** 2,863 of 3,007 draws convert (95.2 %); the rest are 144 point lists
(particles, not converted on purpose). 1,432 distinct geometries, 212,533 triangles. Position formats: 16-bit
half-float x4 (866 geometries), float x3 (458), 2_10_10_10 (62), half x2 (43), float x4 (2), float x2 (1). 78 converted
draws index past their vertex buffer (the Xenos, and ReGPU, read zeros there; e.g. shadow volumes). The wireframes are
right: terrain and rock faces, a grandstand scaffold, an arch bridge, banners, the seated driver
([`m1/stage2-wireframes-2026-11-22.png`](m1/stage2-wireframes-2026-11-22.png)).

This needed one tap fix (ReGPU `vulkan` d540cb0): with baked vertex fetch, ReGPU's default, a translated shader's fetch
layout is empty, so the tap now decodes the vertex fetches from the microcode itself (`ucode::Parse`, `DecodeFetch`),
recording the destination register too; and index data is read through `GpuPhysToGuest` as `BuildIndexList` does.

**Next in stage 2:** the other attributes (normals, UVs, colours: the other fetches, by destination register and the
shader's use), materials from the pixel shaders and textures, and the open items below.

## Stage 2: transforms, camera and the world (2026-11-22)

**Per-draw transforms by running the vertex shader.** [`tools/fir_vs.py`](tools/fir_vs.py) runs a draw's Xenos vertex
shader over its vertices, numerically (numpy, every vertex at once) and symbolically at the same time. Every register
component carries its per-vertex values and a linear form over "atoms": the position fetch's components, or any value
the shader computed non-linearly. oPos then gives each vertex's clip position (ground truth) and, as linear forms, the
shader's last linear map into clip space: a 4x4 "clip from object" matrix when that map takes three atoms. Microcode
decoding is ported from ReGPU (`ucode.cpp`, [`tools/fir_xenos.py`](tools/fir_xenos.py)), op semantics from `hlsl.cpp`:
vector and scalar ALU ops incl. the scalar-constant ops 42-47, predicates (scalar setp and vector setp_push),
exec/cond-exec, jumps, calls and loops with the bool and loop constants, the address register and relative constants
(a0 and aL), and vertex fetches that take their index from their own source register (bone and instance matrices).
A plain symbolic evaluator was not enough: FM3 decompresses most positions non-linearly first (`pos.xyz * pos.w +
c116`), then multiplies by the matrix.

**Result (FM3 grid, single screen, one frame, 2,663 draws):** clip positions for **2,517 draws (94.5 %)**; the rest are
the 144 point lists and 2 draws that fetch textures in the vertex shader. Overlaid on a screenshot taken in the same
frozen boot ([`tools/fir_frame.py`](tools/fir_frame.py) `--shot`), the wireframes match the game: cars, grandstand,
pit building, track edges, hills, tents, the HUD and the rev counter
([`m1/stage2-transforms/overlay-grid-single.png`](m1/stage2-transforms/overlay-grid-single.png)). FM3 draws its scene
into a target that a later pass copies to the screen **rotated 180 degrees** (flipped in x and y): draws up to the
scene pass's resolve (the longest stretch of draws without a resolve) are rotated (`--flip-scene`); later passes
(post, HUD) are not. (A y-only flip looked right at first, because the grid is nearly symmetric: the user caught it.
The giveaway was the dark car in the right lane: mirrored, its wireframe sat on the empty left lane and passed for
a car there. With the rotation, all eight cars of the grid match the screenshot: two staggered columns, the player's
column at view depths 5.4, 17.7, 30 and 42 m, the right one at 11.5, 23.9, 36 and 48 m.)

**Camera and world.** [`tools/fir_world.py`](tools/fir_world.py) takes the camera's view-projection from the most
common clip-from-object matrix among draws whose atoms are the captured position itself (world-space geometry: 168
draws). Decomposed: **53.00 deg vertical field of view, aspect 1.7778, near plane 0.300 (infinite far), rotation error
1.5e-9**; FM3's world is Y-up; clip x is screen-left and clip y screen-down for the scene pass. Every other draw's object-to-world matrix is W = VP^-1 M, from the x, y and w rows (w is
linear view depth; 2 draws write their own depth, the sky dome trick, and are left out). Of the scene pass's 3-atom
draws: 892 rigid, 239 rigid with a mirror in the object matrix (mostly car bodies), 204 with non-uniform scale
(compressed meshes); maps over 2 or 4-8 atoms (about 330 draws) are not exported yet.

**glTF and Godot.** `fir_world.py --gltf` writes the scene pass as glTF: 747 meshes in object space (the atoms'
per-vertex values), 1,253 nodes with their W, and a camera node with the recovered view and field of view; a self-check
projects every node's first vertex through the glTF camera against the capture (median error 3e-9 NDC, 100 % under
1e-3). Godot's glTF import drops a mirror in a node matrix, so mirrors are baked into the vertices and every node
matrix keeps a positive determinant. [`godot/viewer/world_view.gd`](godot/viewer/world_view.gd) loads it at run time
and renders it from the captured camera
([`m1/stage2-transforms/godot-vs-game.png`](m1/stage2-transforms/godot-vs-game.png): the game above, Godot below,
untextured): the left grandstand with its crowd, the people at the garages, cars, drivers, the lamp post,
bridge, tents and hills land where the game has them.

**Materials, first pass (2026-11-22).** `fir_vs.py` now records every export of the vertex shader per vertex, and has
a pixel mode: the pixel shader runs per vertex on those interpolators (pixel register k = vertex export k; pixel
constants at c256+), collecting each non-1D texture fetch with its slot and coordinates. `fir_world.py --gltf` then
takes as the draw's base texture the first 2D fetch whose texture the tap decoded (textures from memory; render
targets made earlier in the frame, such as shadow maps and reflections, are not decoded and are skipped), writes it as
PNG with TEXCOORD_0 and a material, and `world_view.gd --textured` renders the materials unshaded (there are no
normals yet). FM3 grid: 1,019 of 1,335 exported draws textured, 164 textures
([`m1/stage2-transforms/godot-textured-vs-game.png`](m1/stage2-transforms/godot-textured-vs-game.png)).
- **Right:** sky dome, mountains, hills, crowd, barriers, pit wall, bridge, stand structure.
- **Wrong:** the track surface (its shaders blend colour textures through masks: the picked texture is a mask or
  detail map at its own scale), car paint (`b117fbafcc1fa980`, 163 draws: a reflection map, two cube maps and a
  format-54 map, none decoded; the colour comes from constants), the grandstand roof, the car shadow decals (a
  runtime-rendered shadow texture).
- These need **per-shader material rules** (the profile's material archetypes, SCENE_API.md), not a better generic
  guess. [`tools/fir_materials.py`](tools/fir_materials.py) lists the pixel shaders by draw count with their fetches
  (slot, dimension, coordinate register) and each slot's texture (format, size, decoded or not, mean colour): FM3's
  grid frame has 76 pixel shaders in the scene pass, the top 8 cover 820 draws. The undecoded material formats (54,
  and 20 for cube maps) also need decoding in the tap or offline.

**Materials, rules and lighting (2026-11-22, later).** Generic picks get the plain surfaces right; FM3's track and
car shaders need rules, and the first ones are in [`profiles/fm3/materials.json`](profiles/fm3/materials.json) (by
pixel shader): car paint is PS constant c118 (one colour per car: silver, dark green, black, white, blue, yellow,
red, all matching the game) with the livery texture over it by alpha; track line paint is c2 (white, orange, red)
through the decal's alpha; car glass is a dark transparent tint; terrain uses its rock texture; the sky dome is unlit;
the runtime shadow blobs (they read a render target) are left out. Also: draws without a 3-atom map (skinned,
decompressed through several registers: 455 in this frame, including all car paint) are exported in world space
from their clip positions; the alpha mode comes from the render state (source-alpha blending, alpha test, alpha to
coverage); the generic pick skips normal maps; smooth normals. [`tools/fir_pick.py`](tools/fir_pick.py) names the draws
under a screen pixel (shaders, textures), which is how the rules were found. `world_view.gd --lit`: shaded, a sun with
shadows, sky ambient, filmic tonemap
([`m1/stage2-transforms/godot-lit-vs-game.png`](m1/stage2-transforms/godot-lit-vs-game.png)).

**Textures, foliage and materials, second pass (2026-11-22).**
- **Foliage, fences, trusses:** cut-out is now also detected from a kill in the pixel shader (FM3's trees and the
  roof truss have no alpha test in the render state), and a cut-out draw takes the texture whose alpha has a pattern
  (the fence's chain link is its second texture). Blend detection uses the right Xenos factors (6 source alpha, 7
  one minus). Cut-out or blended draws whose textures are all render targets are left out (143).
- **Track:** the line-paint shader is the surface itself: paint colour (c2) over asphalt grey through its mask,
  opaque (no more sky showing through).
- **Lighting from the game:** FM3's sun direction is a PS constant (c250/c136: (-0.714, 0.680, 0.165), 42.8 deg up)
  and goes into the glTF as a directional light (`KHR_lights_punctual`), so Godot's shadows fall as the game's; each
  world draw's baked lightmap (slot 7, its own UVs) becomes the glTF occlusion texture on TEXCOORD_1.
- **Untextured draws** take the median of their pixel shader's output as colour (exhaust tips, trims); car light
  shaders use the clean texture (s14), not FM3's damage texture (s4); glass is nearly opaque dark; car paint has a
  roughness (0.4) so it reflects.
- **Viewer:** a procedural sky for reflections (the visible sky stays FM3's dome), neutral ambient, low specular on
  matte surfaces, filmic tonemap with a little contrast.
- Triple screen with these materials, merged: 263 fps at 3x 2560x1440 with 4x MSAA and shadows (404 materials).
- Still different: the stands' concrete is greyer than the game's warm beige, the hills' rock is warmer than the
  game's grey, asphalt has less grain, and in the merged triple export the CR-X's rear glass shows the interior more
  than in the per-draw export (transparent ordering after merging, to check).

**Third pass: FM3's baked lighting (2026-11-22).** FM3 lights its static world in the pixel shader as albedo x
lerp(c247, c248, lightmap) with a colour lightmap in slot 7 (c247 ambient (0.14, 0.14, 0.18), c248 sun
(1.58, 1.57, 1.50), c242 sky/fog (0.51, 0.69, 0.84); the warm beige of the stands is in the lightmap, not the
textures). `world_view.gd --lit` now renders lightmapped surfaces (513 in the grid frame) the same way: albedo x
lightmap x 1.5 through Godot's detail texture on UV2, unshaded; the cars and other dynamic draws keep Godot's sun
(FM3's direction). Stands, hills (grey rock, dark trees) and the walkway shadows now match the game; the track rules
were retuned for it (asphalt albedo ~0.26, paint 0.75 x c2 over 0.11 grey). Merging now leaves blended draws as
separate nodes: Godot sorts transparency per node, and merged blended meshes drew the CR-X's interior over its glass
(the merged mesh LOD was ruled out). Triple, merged, 4x MSAA and shadows: 250 fps (6,010 draw calls).
Still different: car paint is a little bluer than the game's (the procedural sky in its reflections), kerb paint is
more saturated, the asphalt has less grain.

**Fourth pass: shadows, the hangar, glass (2026-11-22).**
- **No shadows anywhere** had one cause: FM3's sky dome is a mesh around the whole scene and cast a shadow over all of
  it. Unlit surfaces now cast none. The baked world uses a shader (`godot/viewer/fm3_baked.gdshader`): albedo x
  lightmap x gain, no Godot lighting except the sun's shadow (darkens by 0.62), and it casts no shadows itself (its own
  are in the lightmap). So cars and people now shadow the track as in FM3 (the game also lays dynamic shadows over its
  baked world).
- **See-through hangar (and others):** draws with alpha test / alpha to coverage took the texture with an alpha pattern
  as cut-out even when that alpha is a specular mask. Now the pixel shader is re-run with each fetched texture's alpha
  at 0 and at 1 (0 alone fails on foliage cards, whose vertices sit on transparent texels): only a texture whose alpha
  reaches the output alpha drives the cut-out; none (and a conclusive run) = opaque; a render target's alpha = left out.
  Unknown interpolator components are filled with a non-zero value (0 hid dependences). The lightmap slot is never the
  base texture (that was the grey blocks on the hills).
- **Glass:** near-black, alpha 0.9, glossy, with a reflection probe around the grid (FM3 reflects its own environment
  map); the lower hatch panel is opaque black. Viewer: baked gain 1.15, mesh LOD off.
- **Black plastic trim** (window frames, hatch panel, bumper strips, exhaust tips: FM3 shaders `d718f5ba...` and
  `07b55736...`, blended, all their textures runtime environment maps) was left out as unreproducible. Such draws now
  take the pixel shader's own output colour with a dark stand-in for the environment map (Godot's probe adds the
  reflection), kept when the output alpha is ~1 (134 draws).
- Triple, merged, 4x MSAA and shadows: 275 fps.
- Still different: the pit wall in front of the garages is brighter than the game's, the CR-X's wiper is light, asphalt grain.

**The game's own asset files (2026-11-22).** The capture only shows what FM3 drew; its files say what things are.
- **Reading them:** FM3's zips store members as Xbox LZX (method 21). [`tools/fm3unzip/`](tools/fm3unzip/) builds
  `fm3unzip.exe` from the FM3 recomp's own `src/zip.cpp` + `src/lzx.cpp` (`build.cmd`, needs that checkout). Game
  data: `reference/rexglue recomp reference/hl360-forza3/game/disc1/Media` (Disc 1) and the installed Disc 2 / DLC
  packs under its `user/.../Media/DLCZips/*_pri_65.zip` (cars and wheels as `media/cars/<CAR>/<car>.carbin`).
- **Cars:** a `.carbin` keeps each mesh section as a material-name record (u32 2, u32 length, name, u32 1, parameters)
  followed by its index list (big-endian u16, 0xFFFF restarts); vertex and index buffers are uploaded unchanged. So
  [`tools/fm3_assets.py`](tools/fm3_assets.py) finds a captured draw's index buffer (up to 256 bytes) and a piece of
  its vertex buffer verbatim in one car file, and the record before the index list names the material. Over 510 car
  and 567 wheel models (extracted main `.carbin`s), the grid frame's cars are all identified: Honda CR-X Si '91,
  Mitsubishi Eclipse GTS '03, Mazda Axela Sport '05, VW Beetle '04, Chrysler PT Cruiser '04, Hyundai Tuscani '03,
  Ford Focus SVT '03, Citroen C4 VTS '09, plus their wheels (678 draws). Material names: body, bumper_frame,
  rubber_trim, black, frame, plastic2, chrome, chrome_2, window, glass, black_glass, detail_glass_clear/amber/red,
  reflector, tail_light, head_light, interior, badge, emblem, tire, ...
- **Materials by name:** [`profiles/fm3/car_materials.json`](profiles/fm3/car_materials.json) maps them to PBR
  materials (trims black and matte, chrome metallic, windows glass, lenses tinted with the car's
  `shadersettings.xml` values), ahead of the shader-based guesses; `keep` leaves textured parts as they were.
  `fir_world.py` uses it when `FM3_ASSETS` lists the carbin folders (`;`-separated); glTF node names carry
  `car.material`. Fixed by it: the CR-X's black bumper strip (draw 707, `bumper_frame`), chrome exhaust tips, black
  mirrors and frames, lens colours.
- **Tracks:** the grid test runs on **Ladera** (folder `CrownJewel`; the short reverse layout; layouts are the
  `Ribbon_NN` folders). Its `bin.zip` (`fm3unzip`) holds 1,914 `.rmb.bin` model files: world-space vertices (identity
  header matrix) as the GPU draws them; 510 of the frame's 961 track draws find their index list and vertices verbatim.
  Layout decoded in [`tools/fm3_track.py`](tools/fm3_track.py): name, u32 ?, vertex count, stride (16-40), vertices
  (f32[3] position + packed attributes), material name, parameters, prim 3 (strips), index count, u16 indices.
  [`tools/fm3_track_export.py`](tools/fm3_track_export.py) writes the whole site (2,350 meshes, 2.18 M vertices, 511
  materials, ~8 x 7 km) as glTF with stand-in colours by material name; [`fly-track.cmd`](fly-track.cmd) flies it from
  the captured grid camera. It lines up with the capture (grid boxes, pit wall, fences, gantry, bridge, hills).
  Not yet: textures (`.bix`, BIX0 headers, Xbox texture data) and UVs (the packed vertex attributes: their formats
  come from the vertex fetches of the shaders that draw them), the instanced props (grandstands, garages, trees:
  shared `.rmb.bin` models placed by the `.stx.bin` CAFF container's `.data` section), and fewer triangles than the
  strips suggest (243 k from 1.48 M indices: to check).
- **Track textures, first pass (2026-11-22):** the exact mesh layout from ForzaStudio-EVO (FM3-FORMATS.md: LOD, index
  type 6 strip / 4 list, UV offset and tile per mesh; normals 10:10:10; UV0/UV1 u16/65535, **no V flip**) gives all 717 k
  triangles (the first parser lost two thirds). `fir_world.py --material-map DIR` saves each captured draw's base
  texture, lightmap and their UVs; [`tools/fm3_track_texmap.py`](tools/fm3_track_texmap.py) matches draws to track
  meshes by index list and fits the UVs (UV0, UV1 or world-projected): 97 of the track's 511 materials get a texture
  (73 exact), 252 meshes their lightmap atlas placement (scale 1/16 + offset per mesh). `fm3_track_export.py --texmap`
  exports the whole track with them (804 meshes textured, 103 lightmapped). The textures themselves: 245 of the frame's
  377 raw textures are verbatim in `_0x<id>_B.bix` (base level; mips in `_0x<id>.bix`), 33 in the `.stx.bin` static
  pack. Next: decode `.bix` (Xenos untiling + DXT, FM3-FORMATS.md) and find the material -> texture id link (likely the
  `.pvs` model table, which also places the props); tree cards lose their cut-out alpha (black blobs), the pit
  building wall lacks its lightmap.
- **Track textures from the game's files (2026-11-22):** [`tools/fm3_tex.py`](tools/fm3_tex.py) decodes `.bix`
  (BIX0 header, Xenos untiling, DXT1/3/5, DXN, DXT5A, ARGB8, L8, 565) and the `.stx.bin` lightmap atlases; both match
  the captured textures exactly. [`tools/fm3_pvs.py`](tools/fm3_pvs.py) reads the `.pvs` texture table, instances and
  model table. `fm3_track_export.py --pvs <track>_NN.pvs` takes each model's base textures from its shader blocks and
  its lightmap from its 1/16-scale entry: a whole `.bix` when one exists with that id, else the slot in the stx atlas
  whose id range holds the entry (rules in FM3-FORMATS.md). Ladera: 1,978 meshes textured (1,196 from the files), 1,595
  lightmapped; the rock hills, which came out black with the first guess (atlas ids read as `.bix` ids), are now lit.
  Left out: 104 model files placed only by `.pvs` instances (grandstands, garages, trees, barriers), whose placement
  frame is not solved yet.
- **Earlier wrong turn, for the record:** Amalfi GP and Catalunya share props (barriers, flags, shrubs) with Ladera, so
  a few draws matched there too; only the whole-track match settles which track it is.
- **(old notes)** Amalfi GP's `bin.zip` holds 1,151 `.rmb.bin` model files (uncompressed: counts, bounding boxes,
  matrices: placements), 1,824 `.bix` (BIX0 headers: textures) and `AmalfiGP.stx.bin` (a "CAFF 21.11.05" container,

- Still open on cars: the silver Mazda comes out white (its paint constant), the CR-X's wiper is light.

FM3 through ReGPU on the same triple grid: 146 fps (M0). So Godot draws this frame on three screens about twice as
fast with 4x MSAA and shadows. Not comparable yet in everything: a static frame (no game, so FM3's 360 fps engine cap
would apply in a live hookup), everything merged (moving cars must stay separate meshes), no post-processing, and the
look is close to, not the same as, the game. It confirms M0's reading: the scene is cheap for a modern renderer; the
cost is in translating ~9,000 replayed draws per frame.

**Open items:**
- Maps over 4-8 atoms (skinned or morphed meshes) need their object space defined before export.
- The sky dome and other own-depth draws should become a sky in the scene API rather than geometry.
- `fir_world.py`'s reflection search (`drop_reflections`) finds nothing in this frame and can probably go.

Tools for this: [`tools/fir_disasm.py`](tools/fir_disasm.py) (a captured vertex shader's control flow, fetches and
ALU), `fir_frame.py --seqs <file>` (overlay only the listed draws), `fir_world.py --targets` / `--seqs`.

## How to capture

```powershell
$env:REGPU_FIR_CAPTURE = "<file>.fir"   # plus the usual grid / triple variables
# boot, get to the scene, then (FM3 debug server):
tools\fm3ctl.ps1  ->  Fm3 'switch REGPU_FIR_ARM 1'
python -I frame-ir\tools\fir_read.py <file>.fir [--draw N] [--dump-textures DIR]
python frame-ir\tools\fir_frame.py <file>.fir --shot <screenshot.png> --out overlay.png --flip-scene   # numpy: no -I
python frame-ir\tools\fir_world.py <file>.fir --gltf world.gltf [--merge]   # textures go to world_tex\
python frame-ir\tools\fir_pick.py <file>.fir x,y [x,y ...]
python frame-ir\tools\fir_materials.py <file>.fir [--top N]
Godot_v4.7.2-stable_win64.exe --path frame-ir\godot -s res://viewer/world_view.gd -- --gltf world.gltf --out godot.png [--textured | --lit] [--triple bench\g1\layout_auto.json] [--msaa 4] [--bench 600]
```

The script used for the first capture is `m0/results-2026-11-22/fircap.ps1` (`-Shot <png>` takes a screenshot
before arming; `-Mode single` for a single-screen capture, which the transform tools assume).
